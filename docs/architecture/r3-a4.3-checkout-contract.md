## 2. Base that does not change

Taken literally from the source: *"Base que no cambia: las reglas operativas 1 a

### 2.1 Operational rules 1–5

1. The UI must show **"Cobro reservado"** and the reservation must be persisted
   **before** operating the POS terminal or accepting a transfer.
2. A foreign close (not the initiator) is allowed only for an OWNER/ADMIN
   authorized at the location, with reason and evidence.
3. Unconfirmed cash is not moved informally: confirm the original intent or
   return it, with a declaration in the same transaction.
4. **No automatic expiry of the charge reservation.** Recovery/close is manual.
   (The *stock* reservation does expire and is swept as before.)
5. Ordinary confirmation is only by the initiator; supervisor intervention is
   exceptional, with reason, evidence and audit in the same transaction.

### 2.2 Proportional engine and money

- All money is integer minor units (centavos) in `BigInt`; never `Number` for
  money.
- The proportional engine and the price-mode rules of Pilot Pricing V2
  (`AGENTS.md` 2026-10-06) are unchanged.
- Approved proportional methods are **CASH, TRANSFER, CARD_DEBIT**. QR and the
  card/credit modes are outside this increment.

## 3. States and transitions (§1)

Single enum, shared by `CheckoutAttempt.status` and `SaleCheckout.attemptStatus`
with the same PostgreSQL type:

```
CheckoutAttemptStatus = RESERVED | CONFIRMED | REJECTED | ABANDONED
```

| Transition | Who | Transaction |
| --- | --- | --- |
| (nothing) → RESERVED | the initiator | T-R |
| RESERVED → CONFIRMED | the initiator, or a supervisor exceptionally (rule 5) | T-C |
| RESERVED → REJECTED | whoever submitted the confirmation, on a terminal rejection | T-C (confirmed rejection) |
| RESERVED → ABANDONED, with declaration | the initiator or a supervisor | T-X |
| REJECTED without declaration → declared | the initiator or a supervisor | T-X |
| RESERVED → RESERVED, with stock re-secured | only a supervisor | T-S (new) |

No other transition exists. `CONFIRMED` is immutable. There is no automatic
expiry (rule 4).

- **Open attempt** = `RESERVED`, or `REJECTED` without declaration. There is at
  most one per sale, guaranteed by the schema (partial unique index).
- **`stockState`** is computed at read time and never stored:
  - `VALID` — `ACTIVE` stock reservations cover the lines and have not expired.
  - `EXPIRED` — `ACTIVE` coverage exists but with `expiresAt <= now`.
  - `RELEASED` — no `ACTIVE` coverage, total or partial (sweeper or B1/B2
    released it).
  - `INCONSISTENT` — a reservation from another branch, or with quantity ≤ 0.

## 5. Canonical hashes and DTOs (§4)

Hashes are SHA-256 over the exact ASCII bytes of a text where **every line
ends in `0x0A`, including the last**, no BOM and no spaces; the result is
lowercase hex, 64 characters.

| Field | Format |
| --- | --- |
| UUID | lowercase, with hyphens |
| Integer | ASCII decimal, unsigned, no leading zeros |
| Absent | `-` |
| Enum | its ASCII name |

Two canonical texts exist: the **plan** (`mona-checkout-plan/v1`) and the
**confirmation** (`mona-checkout-confirmation/v1`). `planHash` is `CHAR(64)`;
`confirmationHash` is `CHAR(64)`, and `CheckoutAttempt_confirmation_key`
(`operationKey, saleId, status, confirmationHash`) is the idempotency key.

S2 fixed reference vectors (text → hash), including a case with non-ASCII
`institutionOther`.

DTO notes: reservation, confirmation and close do not change relative to the
consolidated contract; UUIDs are lowercase canonical and amounts are
`BigInt` strings. Stock recovery: `{reserveKey?: uuid, reason: string(10..500),
evidence: string(3..200)}`.

### 6.1 C3 — the supervisor predicate (§4.3)

```ts
export function actsAsSupervisorAtLocation(ctx: Ctx, permissions: readonly string[], locationId: string): boolean {
  if (!locationId || permissions.length === 0) return false;
  if (isOwner(ctx)) return true;                       // OWNER: only a valid company assignment
  return ctx.assignments.some((a) => a.roleCode === ROLE_CODES.ADMIN
    && a.scopeKind === 'COMPANY'
    && permissions.every((p) => a.permissions.includes(p)));   // all in the SAME assignment
}
```

- `locationId` is always `sale.branchId`, read under lock.
- An ADMIN with branch scope, or with the permissions spread across several
  assignments, does **not** qualify.
- No permission suffices on its own without the effective role.

This is an **authority predicate**, not a sixth role. The five Production V1
roles are unchanged.

### 6.2 Action permission matrix (§4.3)

| Action | Initiator | Supervisor (reason + evidence + audit in the same transaction) |
| --- | --- | --- |
| Reserve | `SALE_CHARGE` and `SALE_COMPLETE` at the branch | — |
| Confirm | the initiator, with `SALE_CHARGE` and `SALE_COMPLETE` at the branch | `[SALE_CHARGE, SALE_COMPLETE]` |
| Close or declare | the initiator, with `SALE_CHARGE` at the branch | `[SALE_CANCEL_PENDING]` |
| Recover stock (T-S) | cannot | `[SALE_CORRECT_PENDING, SALE_CHARGE]` |
| GET per sale and `recent?scope=mine` | `SALE_CHARGE` at the branch | same |

### 7.2 Recent-attempts query (C4)

- Read without locks. `limit <= 50`; `since >= now − 7 days`; default window 24

## 8. Lock order

The fixed order, never inverted (from §5 of the final corrections):

```
Sale
→ CheckoutAttempt
→ ExternalCollection (id ASC)
→ CashSession
→ StockReservation (id ASC)
→ Inventory (id ASC)
```

The `ORDER BY id ASC` in the `ExternalCollection`, `StockReservation` and
`Inventory` locks is the ORDERING REQUEST, not proof of the physical sequence the
PostgreSQL executor actually takes: a bitmap/heap plan could still acquire row
locks in a different physical order. That guarantee needs real PostgreSQL
evidence and is recorded as **PostgreSQL evidence pending P21+** (F4 of the S5-D
audit); it is neither claimed here nor forced by a planner hint or an advisory
lock. The bounded retries on `P2034` / `40001` / `40P01` remain mandatory.

## 10. Procedures not fully implemented / not PostgreSQL-verified (§11)

Stated explicitly in the approved source:

1. **External refund: implemented DB-free, NOT PostgreSQL-verified.** S-REF
   implements the `UNAPPLIED → REFUNDED` endpoint (T-F) and the branch listing;
   see §11. There is still **no** POS/bank integration and **no** automatic
   reimbursement: the refund is a manual, supervised registration. Whether the
   F6 trigger, `chk_ec_status` / `chk_ec_refund_fields` / `chk_ec_claim_state`
   and the real row lock accept T-F exactly as designed is **NOT verified**
   (P36–P40 **NOT RUN**; Codex not re-reviewed).
2. **A general listing of `UNAPPLIED` collections by branch now exists**
   (`GET /api/v1/external-collections`, S-REF): a supervisor reads the whole
   branch, a `SALE_CHARGE` holder without supervisor authority reads only the
   rows it recorded. The listing permission never enables the refund.
3. **A decision the OWNER must make before opening:** how to proceed meanwhile
   (e.g. manual POS void or manual transfer return with a signed external record
   and daily reconciliation). The system can now mark those refunds once S-REF is
   PostgreSQL-verified and approved.
